# 性能验证方法：比跑出一个大数字更重要

## 吞吐判定必须看连续 LAG

驱动宣称的发送速率不等于服务端可持续吞吐。判断某个固定负载是否可持续，需要同时确认：

1. 驱动实际发送成功率；
2. Kafka 消费组 LAG 的连续时间序列；
3. 测量结束后是否仍有足够积压；
4. 应用和下游资源水位；
5. DLQ 与错误日志是否异常增长。

单个 LAG 点或首尾两个点可能正好落在批量 flush、compaction 或瞬时排空阶段，不能据此判断“跟得上”。

## 排空法必须有足够积压和预热

测量最大消费能力时，先准备远大于测量窗口可排空量的积压，启动后完成 JIT、连接建立和缓存预热，再计算固定窗口内的 LAG 差值。

如果测量中途积压见底，得到的只是生产端供给能力；如果把启动阶段混入窗口，得到的又是冷启动与稳态的混合值。

## A/B 一次只改变一个变量

一个有效的写入配置 A/B 必须固定负载、消息模型、分区和应用参数，只改变一个 GreptimeDB 或客户端参数。批大小阶梯也必须保持消息形态、分区和积压方法一致。

同时修改线程、批次、数据库配置和消息模型，即使吞吐提高，也无法判断收益来自哪里，更无法知道可靠性代价由哪个变化引入。

## 必须证明进程运行的是新代码

多模块构建中，编译 `classes` 不一定重建运行时引用的 jar。曾出现源码已修改、运行进程仍加载旧 jar，却因为采样噪声得到“优化符合预期”的假阳性。

性能复测前必须检查运行中 JVM 的类和方法，确认新实现确实被加载。构建成功、文件时间戳和源码 diff 都不能替代这个检查。

## GC 必须比较对齐的稳态窗口

启动、设备建档和缓存预热的分配强度远高于稳定遥测。用“累计 GC 次数 ÷ JVM uptime”比较两个运行时，如果两次 uptime
不同，会把启动阶段占比误认为代码性能变化。

正确方法是在相同负载下选取对齐的稳态窗口，比较窗口内分配速率、GC 次数、停顿时间和堆回落幅度。

## 先观测，再决定是否改

线程数、连接池、批大小和缓存容量都可能“看起来过大”。但空闲不是立即缩小的充分理由，故障恢复和连接重建可能使用健康场景下看不到的资源。

项目先增加 writer wait、Redis roundtrip、批次耗时、收敛耗时、在线跳变延迟等指标，再根据压测结果集中定值。没有观测依据的数字保留为初值，而不是逐处凭直觉微调。

## 负结果同样重要

性能工作需要记录被证伪的假设：

- 更多消费者没有引入预期中的业务锁竞争；
- Kafka 虚拟线程 pinning 在高分区高吞吐下没有显著放大；
- 某些看似昂贵的异常栈优化没有测出可区分收益；
- 工作集保留时间并不一定是 CPU 杠杆；
- 继续增加消费者可能只增加下游 CPU，不再增加吞吐。

这些结论可以阻止团队重复做无效优化，也能让真正的瓶颈保持清晰。

## 对外发布性能数字的规则

任何公开数字都应携带：

- 版本或测试日期；
- CPU、内存和磁盘；
- 单机还是分布式部署；
- Kafka Broker、分区和副本；
- 设备数量和消息形态；
- 测量是稳态输入还是积压排空；
- 已知未覆盖场景。

宁可报告“300k QPS 稳定通过、350k QPS 未通过，边界位于 `[300k, 350k)`”，也不要把通过档包装成精确上限，或因为失败档最终能够排空就宣称它可以持续运行。
