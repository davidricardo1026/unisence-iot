# 统一感知物联网系统：轻松支持百万设备、百万 QPS，打造属于自己的物联网平台

**统一感知物联网系统（Unisence IoT）** 是一套高性能、功能完整、可扩展的物联网基础平台。

开源地址：[GitHub](https://github.com/davidricardo1026/unisence-iot) · [Gitee](https://gitee.com/david0624/unisence-iot)

它不是只有设备列表和几张图表的管理后台，而是把物联网平台真正需要的数据主链路一次搭好：*
*产品与设备管理、物模型、设备接入、实时数据处理、时序存储、在线状态、规则引擎、数据路由、权限与管理控制台**，全部围绕百万设备、百万
QPS 的规模化数据处理设计。

平台通过服务分进程部署和水平扩展承载百万 QPS；百万设备场景采用紧凑版本目录、有界缓存与分片在线状态，避免把百万完整设备对象或状态集中到单个进程、单个缓存键中。

支撑这一能力的直接单机证据：

> **单机全链路实测 300,004 QPS，连续运行 5 分钟稳定通过。**

这不是只把消息发进 Kafka 的发送速度。测试同时覆盖设备消息接入、物模型校验、GreptimeDB 时序写入、设备在线状态、2 条即时规则、2
条窗口规则、规则状态事务与规则结果输出。5 分钟内发送 90,002,829 条负载消息，发送失败 0，最终 DLQ 0、重复消息 0，数据引擎消费
LAG 全程为 0，规则 LAG 主动回落并最终归零。

更重要的是，这个结果没有靠堆叠应用实例、放松 Kafka 事务语义或无界扩大线程池换取：driver、engine、rule-stream 各只有一个
JVM，Kafka 是单 Broker（RF=1），GreptimeDB 为单实例，MySQL 与 Redis 也均为单节点，且全部与应用和压测端部署在同一台机器。中间件尚未围绕该机器逐项完成极限容量专项调优，系统已经稳定站上
**30 万 QPS**。当前单规则服务实例的稳定处理边界为 **[300k, 350k) QPS**；数据引擎在 350k 对照档依然没有积压，继续优化与横向扩展仍有空间。

## 高性能，不牺牲可靠性

统一感知不是用“少做事情”换出一个好看的数字。30 万 QPS 对应的是从消息接入到存储和规则输出的完整业务链路，关键可靠性机制全部开启：

- **成功后再提交消费位点**：GreptimeDB 等下游短暂不可用时保留 Kafka 消息，恢复后继续重放；
- **规则事务原子提交**：规则状态、全部目标 Topic 输出、DLQ 与输入 offset 同时成功或同时回滚；
- **同一设备分区有序**：统一 Kafka key 保持设备消息在 Topic 内的处理顺序；
- **有界并发**：批处理、固定执行器和明确的队列上限，不用无限线程和无限缓存制造虚假吞吐；
- **本地元数据热路径**：产品、物模型、设备和规则构建不可变本地快照，高频消息不逐条访问 MySQL；
- **故障可重放**：进程重启或分区迁移后，从已提交边界恢复规则状态并继续消费。

平台采用 Java 21、Vert.x、Kafka、Redis、MySQL 与 GreptimeDB 构建。设备接入、数据引擎、规则服务和管理端分进程部署，可以根据实际瓶颈独立扩容。

## 即时规则，拿来就能跑

即时规则是平台默认提供的规则能力。从创建、校验、启停、运行到 Kafka 输出形成闭环，可以直接用于设备告警判断、数据加工和业务事件生成。

即时规则支持：

- **属性与事件规则**：按消息类型、产品和物模型标识符精确监听；
- **六种阈值判断**：`>`、`>=`、`<`、`<=`、`==`、`!=`；
- **Groovy 脚本条件**：支持枚举状态、多字段组合等普通阈值无法表达的业务条件；
- **前置过滤脚本**：先过滤无关消息，再进入判档与输出阶段；
- **多级告警档位**：一条规则可配置提示、预警、严重等多个档位，并按严重度确定判定优先级；
- **自动升档、降档与恢复**：设备从正常到异常、异常升级、异常缓解以及恢复正常都有明确事件；
- **档位跃迁去风暴**：持续停留在同一档位时不重复输出，边界抖动还可配置冷却；
- **两种输出模式**：`LEVEL_TRANSITION` 适合状态变化与告警，`EVERY_MATCH` 适合每条命中消息都加工后转出；
- **输出转换脚本**：按业务需要生成结构化 payload，无需修改平台核心代码；
- **JSON 与 MessagePack**：按下游消费方式选择输出编码；
- **一档多 Topic 输出**：同一次规则触发可原子写入多个已登记 Kafka Topic；
- **可选错误策略**：支持进入 DLQ、跳过当前规则或按明确的数据过滤策略丢弃；
- **保存时校验与脚本预编译**：配置、物模型引用和脚本问题尽量在规则生效前暴露。

即时规则的两类典型用途都已经覆盖：

1. **设备告警**：温度进入预警档、继续升到严重档、下降到预警档、最终恢复正常，只在状态变化时输出，避免持续高温造成告警风暴；
2. **实时数据加工**：每条符合条件的属性或事件执行转换脚本，再分发到一个或多个业务 Topic，供告警中心、工单、数据湖或其他系统消费。

需要分钟均值、累计值、次数统计、滑动窗口、去重或到期结算时，可叠加窗口运行时。窗口能力的安装与使用说明见[版本能力说明](edition.md)。

## 物联网底座该有的核心能力，一套带齐

### 产品、设备与物模型

- 产品与设备统一管理；
- 设备标签与自定义设备表单；
- 属性、事件和服务物模型定义；
- 属性标识符、数据类型、读写方式、单位与约束管理；
- 设备详情、当前属性、历史属性、事件和上下线记录查询。

### 设备数据接入

- 统一的强类型消息契约；
- MessagePack 紧凑编码，降低高频遥测的传输与解析开销；
- 支持设备建档、属性上报、事件上报、设备心跳和驱动服务心跳；
- 驱动公共库统一处理 Kafka key、header、编码和发送确认；
- 新协议只需实现协议解析与标准消息映射，不必重写存储、在线状态和规则链路。

### 时序数据与在线状态

- GreptimeDB 统一存储属性当前值、属性历史、设备事件与上下线记录；
- 属性按数据类型与保留策略写入；
- 高频活跃信号在进程内合并，只有真实上线、离线变化才记录状态跳变；
- 历史曲线、趋势降采样和分页查询均由管理端提供统一入口；
- 设备准入先于落库，未注册设备不会污染时序数据。

### 数据路由与系统集成

- 按产品和消息类型配置透传路由；
- 确认时序数据写入成功后再向业务 Topic 转发；
- MessagePack 透传可直接复用原始消息字节、key、header 和时间戳；
- 规则输出与透传 Topic 统一登记治理，方便接入告警、工单、报表、数据湖和行业应用。

### 管理与运维基础能力

- Vue 3 + TypeScript 管理控制台；
- 用户、角色、菜单与按钮权限；
- 字典、操作日志等通用管理能力；
- 元数据增量同步、缓存回源与 Last Known Good 快照；
- 数据质量错误进入 DLQ，并提供分类指标与受控日志，便于定位问题。

平台当前聚焦设备上行数据主链路。物模型服务可以定义，但设备服务调用、远程配置与下行命令链路尚未交付；平台不自带正式
MQTT、Modbus、OPC UA 协议驱动，可基于驱动公共库自行接入，或安装对应驱动组件。

## 特别适合做自己的物联网平台底座

统一感知已经把最重、最容易踩坑的底层工作做好：高吞吐消息链路、设备准入、物模型校验、时序存储、在线状态、实时规则、可靠重放、事务输出和元数据同步。

在此基础上，可以直接打造：

- 工业设备监控平台；
- 能源管理与能耗分析平台；
- 智慧园区、智慧楼宇和环境监测平台；
- 设备运维、故障预警与预测性维护系统；
- 车联网、充电设施或分布式终端管理平台；
- 面向具体行业的 IoT SaaS 与数据中台。

业务团队可以把重点放在协议适配、行业模型、告警闭环、可视化大屏和客户业务流程上，而不是重新解决 Kafka
消费、时序表设计、设备在线判定、规则状态一致性这些底层问题。
