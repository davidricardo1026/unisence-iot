# 性能基准：单机全链路稳定能力不低于 300k QPS

## 当前结论

当前 GreptimeDB 全链路单机压测已经验证：

| 场景                     |                             结果 |
|------------------------|-------------------------------:|
| 200k QPS               |                           稳定通过 |
| 250k QPS               |                           稳定通过 |
| 300k QPS               |        实际 **300,004 QPS**，稳定通过 |
| 350k QPS               | 实际 349,994 QPS，规则 LAG 持续增长，未通过 |
| 当前单 rule-stream 实例稳定边界 |           **[300k, 350k) QPS** |

300k 档持续发送 5 分钟，虚拟驱动发送 90,002,829 条负载消息，失败为 0。加上 10,000 条设备建档消息后，Kafka 输入与规则服务接收均为
90,012,829 条，DLQ 和重复消息均为 0。规则 LAG 早期达到 425,493 后主动回落并保持有界，停止发送时归零；数据引擎的属性和事件消费组
LAG 全程为 0。

350k 档中，虚拟驱动同样准确达到目标且失败为 0，数据引擎两个消费组仍无积压，但规则 LAG 在负载期持续增长到 6,202,522。停止发送后约
18 秒归零不能把该档判为稳定，因为持续业务不会提供排空窗口。

因此，当前可以严谨声明“单机全链路轻松稳定处理 10 万 QPS，并已验证 30 万 QPS 稳定吞吐”，但不能把 35 万 QPS 写成稳定能力。

| 项目         | 配置                                         |

| CPU        | Intel Core i9-13980HX，24 核 / 32 线程         |
| 内存         | 约 62.4 GiB                                 |
| 存储         | NVMe                                       |
| JDK        | OpenJDK 21.0.9                             |
| Kafka      | 4.3.1，单 Broker，RF=1                        |
| GreptimeDB | 1.3 单实例                                    |
| MySQL      | 8.0                                        |
| Redis      | 独立运行数据库 DB 6                               |
| 应用         | driver、engine、rule-stream 各一个 JVM；窗口运行时已安装 |

应用和中间件运行在同一台机器。同机部署省去了真实网络跳转，却也让 Kafka 日志、GreptimeDB 数据、应用和压测端竞争同一组
CPU、内存与磁盘，因此不能按固定倍数换算生产容量。

## 消息与规则模型

- 10,000 台设备；
- 90% 属性消息，每条包含 `temperature`、`pressure` 两个 double 属性；
- 10% 事件消息，在两种事件之间均匀分布；
- 2 条即时规则、2 条窗口规则；
- engine 单进程，属性和事件链路各使用 4 个消费者；
- rule-stream 单进程，使用 4 个分区 worker；
- 每档正式负载持续 5 分钟，驱动使用 8 个发布线程；
- 输入 Topic 为 48 个属性分区和 12 个事件分区。

## 为什么以 LAG 曲线判定

驱动发送速度只证明 Kafka 能够接收消息，不能证明服务端可持续处理。每档同时检查：

1. 驱动实际发送速率、失败数与最终在途数；
2. engine 属性与事件消费组的连续 LAG；
3. rule-stream 消费组的连续 LAG；
4. 停止发送后的排空时间；
5. 输入、消费、输出、DLQ 和重复消息对账；
6. 应用日志、JVM、Kafka 与 GreptimeDB 资源水位。

300k 档的 LAG 虽有高振幅，但会主动回落并保持有界；350k 档则在正式窗口内近似单调增长。这一区别比最终是否能排空更能代表持续处理能力。

## 当前瓶颈边界

350k 档中，engine 属性和事件 LAG 全程为 0，积压只出现在单实例 rule-stream。因此该档不能用于推断 GreptimeDB
写入上限，也不能把规则服务的单实例边界表述成整个平台所有模块的共同上限。

当前结果没有通过增加实例、放松 Kafka 事务语义或无界扩大线程池取得。规则状态、输出、DLQ 与输入 offset 仍在同一个 Kafka 事务内提交。

## 尚未证明的能力

当前测试尚不能回答：

- 100 万设备同时活跃时的目录内存、缓存命中率和恢复时间；
- 每条消息包含 20 个属性时的 GreptimeDB 写入能力；
- 3 Broker、RF=3 下的复制与事务成本；
- 多实例 rule-stream 的重平衡、状态恢复与横向吞吐；
- 长稳运行、低流量端到端延迟和故障注入；
- 热点设备、复杂脚本和不同窗口放大因子的组合上限。

生产部署前必须使用真实消息、规则、热点分布、网络和副本策略重新执行阶梯压测。完整判定原则见[性能验证方法](performance-methodology.md)。
